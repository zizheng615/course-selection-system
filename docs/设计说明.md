# 高校选课管理系统 — 设计说明

> 技术栈：Python 3.11+ / FastAPI / SQLite / 原生 ES Module 前端
> 功能基准：与参考项目（Vue 3 + Spring Boot 3 + MySQL 8 版本）逐项对齐

---

## 1. 需求概述

系统的核心是一句话：**有限的课容量被多个学生并发争抢**。
围绕它展开的全部功能可以分成四块。

| 角色 | 需求 |
|---|---|
| 管理员 | 维护课程与上课时间、维护学生与教师、维护账号、查看与干预选课记录、查看统计报表 |
| 教师 | 查看自己所授课程、查看课程学生名单、录入与修改成绩 |
| 学生 | 浏览可选课程、选课、退课、查看课表与成绩 |
| 全体 | 通过 AI 助手了解系统怎么用（回答需按角色隔离） |

从需求里提炼出三个**技术难点**，它们决定了本项目的设计重心：

1. **并发安全**：同一门课最后几个名额被多人同时点「选课」，不能超卖。
2. **时间冲突**：判定「两门课是否冲突」是区间重叠问题，不是简单的相等比较，
   而且要在「可选课程列表」「冲突反查」「选课校验」三处保持一致。
3. **可扩展**：新增一个 AI 回答来源、新增一个 REST 模块、新增一个前端页面，
   都不应该去改动已有代码。这是题目对开闭原则的要求。

## 2. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | Python 3.11+ | 标准库自带 `sqlite3`，无额外数据库驱动 |
| Web 框架 | FastAPI + uvicorn | 自带 OpenAPI 文档；依赖注入天然适合做声明式鉴权 |
| 校验 | pydantic v2 | 入参校验与错误定位由框架完成，Service 只处理业务规则 |
| 数据库 | SQLite（WAL 模式） | 单文件、零部署；WAL 允许读写并发 |
| 密码 | bcrypt | 自带盐值，抗彩虹表 |
| 令牌 | PyJWT（HS256） | 无状态，不引入会话存储 |
| 前端 | 手写 HTML/CSS/原生 ES Module | 无 npm / Node / CDN 依赖，`pip install` 后即可运行 |
| 校验工具 | `sql/03_queries.sql` + `scripts/run_queries.py` | 用一致性自检查询验证冗余计数不跑偏，随包可复现 |

选型的第一原则是**零外部依赖**：评审老师拿到压缩包后只需 `pip install -r requirements.txt`，
不需要装 MySQL、不需要联网、不需要 Node 环境。

## 3. 总体架构

### 3.1 分层

```
                     ┌──────────────────────────────────────┐
   HTTP 请求  ──────▶ │ routers/    控制器层                  │
                     │  · 路径与参数绑定（pydantic）          │
                     │  · 鉴权：Depends(require_role(...))   │
                     │  · 不含业务判断                        │
                     └───────────────┬──────────────────────┘
                                     │
                     ┌───────────────▼──────────────────────┐
                     │ service/    业务层                    │
                     │  · 业务规则与错误码                    │
                     │  · ★ 事务边界只在这一层 ★              │
                     │  · 编排多个 repository 调用            │
                     └───────────────┬──────────────────────┘
                                     │
                     ┌───────────────▼──────────────────────┐
                     │ repository/ 数据访问层                 │
                     │  · 只写 SQL，返回行字典                │
                     │  · 不开事务、不做业务判断              │
                     └───────────────┬──────────────────────┘
                                     │
                     ┌───────────────▼──────────────────────┐
                     │ SQLite（WAL）  6 表 2 视图            │
                     └──────────────────────────────────────┘
```

分层带来两个具体好处，而不只是「看起来整齐」：

* **事务边界唯一**。所有 `BEGIN IMMEDIATE` 都出现在 `service/` 里，
  排查「哪里可能死锁」只需要看一层代码。
* **SQL 集中**。索引有没有被用上，去 `repository/` 一处看即可，
  而且 `EXPLAIN QUERY PLAN` 的优化对比（见 `sql/03_queries.sql`）能直接对着这一层做。

### 3.2 请求的完整生命周期

以「学生选课」为例：

```
POST /api/enrollments  {courseId: 17}
  │
  ├─ routers/enrollment.py    取当前用户（require_role(STUDENT)）
  ├─ service/enrollment_service.py
  │    ├─ BEGIN IMMEDIATE                     ← 事务开始，立刻拿写锁
  │    ├─ 查课程是否存在 / 是否 OPEN / 是否同学期
  │    ├─ 查是否已有记录（SELECTED 直接报 4002；WITHDRAWN 走复用）
  │    ├─ 查时间冲突（SQL 区间重叠）
  │    ├─ UPDATE course SET enrolled_count = enrolled_count + 1
  │    │    WHERE id = ? AND status = 'OPEN' AND enrolled_count < capacity
  │    ├─ rowcount == 0 → 回滚，返回 4004（名额已满）
  │    ├─ INSERT / UPDATE enrollment
  │    └─ COMMIT
  └─ common/result.py         统一包成 {code, message, data}
```

## 4. 数据库设计

### 4.1 实体关系

```
   sys_user (统一账号)
      │ 1
      ├──────────┐
      │ 1        │ 1
   student    teacher
      │ 1        │ 1
      │          │
      │ *        │ *
      └──▶ enrollment ◀── course
                  *   │ 1
                      │ 1
                      *
                course_schedule
```

**为什么账号与业务分表？** 三种角色共用一张 `sys_user` 做认证，
业务属性（学号/专业/年级、工号/职称/院系）各自放在业务表。
好处是登录逻辑只需要查一张表，而业务表的字段可以各自演进，互不影响。
代价是新增一个学生要同时写两张表 —— 这个代价被 `student_service` 里
「新增学生自动建号」的一个事务吸收掉了。

### 4.2 表结构要点

| 表 | 职责 | 关键字段 |
|---|---|---|
| `sys_user` | 认证、角色、启用状态 | `username` 唯一、`role`、`status` |
| `student` | 学生业务信息 | `student_no` 唯一、`user_id` 唯一外键 |
| `teacher` | 教师业务信息 | `teacher_no` 唯一、`user_id` 唯一外键 |
| `course` | 课程与容量 | `(course_code, semester)` 唯一、`enrolled_count` 冗余计数 |
| `course_schedule` | 上课时间（一门课可多段） | `weekday`、节次区间、周次区间 |
| `enrollment` | 选课记录 | `(student_id, course_id)` 唯一、`status`、`score` |

### 4.3 三处「有意为之」的设计

**（1）`enrolled_count` 反范式**

余量 = `capacity - enrolled_count`。如果每次列表都去 `COUNT(*)` 一遍选课记录，
课程列表页会退化成 N 次聚合查询。冗余一个计数列之后，列表查询变成单表扫描。

一致性靠三层保证：

* 数据库：`CHECK (enrolled_count >= 0 AND enrolled_count <= capacity)` —— 拦下越界；
* Service：所有增减都走同一条原子 `UPDATE ... WHERE enrolled_count < capacity`；
* 自检：`sql/03_queries.sql` 里有一条「`enrolled_count` 与真实选课数是否一致」的查询，
  干净数据下必须返回空集。`scripts/init_db.py` 每次建库都会跑它。

**（2）`uk_student_course` 唯一索引**

防重复选课的最终兜底。它的存在直接决定了**退课必须是软退课**：
如果退课删行，学生重新选同一门课就会插一条新行，与唯一索引冲突。
所以退课只把 `status` 改成 `WITHDRAWN`，重新选课时把同一行改回 `SELECTED` 并清空旧成绩。

**（3）`course_schedule` 独立成表**

一门课可能有理论课 + 实验课两段上课时间，它们一起进入学生课表，也一起参与冲突判定。
如果把时间做成 `course` 表的字段，就无法表达多段，冲突判定也没法用区间比较。

### 4.4 索引

| 索引 | 服务的查询 |
|---|---|
| `uk_username` | 登录 |
| `uk_student_no` / `uk_teacher_no` | 按学号/工号查询与唯一性 |
| `uk_code_semester` | 课程唯一性；`(course_code, semester)` 前缀也可用于按代码查 |
| `idx_semester_status` | 课程列表的「学期 + 状态」筛选 —— 最常用的组合条件 |
| `idx_teacher` | 教师查自己的课 |
| `idx_cs_weekday` | **冲突检测**：按 `(weekday, start_section, end_section)` 缩小候选集 |
| `idx_enroll_course_status` | 课程学生名单、容量统计 |
| `idx_enroll_student_status` | 学生的「我的课程」「我的课表」 |
| `idx_major_grade` | 学生列表按专业筛选 |

`sql/03_queries.sql` 里有若干条 `EXPLAIN QUERY PLAN` 的前后对比
（含 `NOT INDEXED` 强制全表扫描的对照组），用来证明索引确实被用上了。

### 4.5 视图

| 视图 | 用途 |
|---|---|
| `v_course_detail` | 课程 + 教师姓名 + 职称 + `remaining`。前端课程列表直接查它，避免每次都手写 JOIN |
| `v_student_credit` | 学生学分统计。用 `LEFT JOIN` 保证**没选课的学生也出现在结果里** |

## 5. 核心业务设计

### 5.1 认证与权限

* 口令用 bcrypt 存储，登录时 `bcrypt.checkpw` 校验。
* **账号枚举防护**：账号不存在与口令错误返回**同一条提示**，避免攻击者靠错误文案
  枚举出系统里有哪些账号。
* 禁用账号（`status = 0`）在签发令牌前就被拦下。
* JWT 载荷里带业务主键 `refId`（学生 ID / 教师 ID），省掉每次请求再查一次映射。
* 令牌失效与越权分开报错（`1002` / `1003`），前端据此决定「跳登录页」还是「提示无权限」。

权限用**声明式依赖**表达，而不是在 Service 里写 `if`：

```python
@router.post("", dependencies=[Depends(require_role(Role.ADMIN))])
def create_course(payload: CourseCreate, ...): ...
```

`require_role` 是一个依赖工厂，返回一个依赖函数。改权限 = 改一行装饰参数，
不需要进函数体。这也是开闭原则在鉴权维度的体现。

### 5.2 并发选课与防超卖

**问题**：两个请求同时读到「余量 1」，各自判断「还有名额」，然后都去 `+1`，
结果 61 个人选进了 60 个座位的课。

**天真的做法**（有竞态）：

```python
course = repo.find(course_id)          # 读到 enrolled_count = 59
if course.enrolled_count < course.capacity:   # 两个请求都通过
    repo.update_count(course_id, course.enrolled_count + 1)   # 都写 60
```

**本项目的做法**：把判断塞进 `UPDATE` 的 `WHERE`，让数据库在**同一把锁内**
完成「判断 + 修改」，然后只看影响行数：

```sql
UPDATE course
   SET enrolled_count = enrolled_count + 1
 WHERE id = ?
   AND status = 'OPEN'
   AND enrolled_count < capacity
```

```python
if cursor.rowcount == 0:
    raise BusinessError(ErrorCode.COURSE_FULL)   # 没抢到，事务回滚
```

`rowcount` 为 0 有两种可能：课程被关掉了，或者名额满了。
两种情况本来就都该拒绝，所以不需要再区分。

**SQLite 侧的配合**：

| 措施 | 作用 |
|---|---|
| `PRAGMA journal_mode = WAL` | 读不阻塞写，写不阻塞读 |
| `PRAGMA busy_timeout = 10000` | 抢不到锁时等 10 秒而不是立刻报 `database is locked` |
| 写事务用 `BEGIN IMMEDIATE` | **一开始就申请写锁**，避免「先读后写」时锁升级失败 |
| 连接按线程隔离 | `sqlite3` 连接对象不能跨线程共享 |

开发阶段用多线程模拟过抢课：N 个线程抢 K 个名额，成功次数恰好等于 K，
且结束后 `enrolled_count` 与真实选课记录数完全一致。
随包可复现的验证手段是 `sql/03_queries.sql` 里的容量一致性自检查询。

### 5.3 时间冲突判定

两门课冲突 ⟺ 同一学期、同一天、**节次区间重叠**、**周次区间重叠**。

区间重叠的标准判定（不是「起点相等」，两段部分交叠也算冲突）：

```
A.start <= B.end  AND  B.start <= A.end
```

直觉解释：A 在 B 结束之前就开始了，且 B 在 A 结束之前也开始了 —— 两者必然交叠。

应用到本系统：

```sql
-- 学生冲突：节次 + 周次两个维度都要重叠
SELECT ... FROM course_schedule a
  JOIN course_schedule b ON b.weekday = a.weekday
 WHERE a.course_id = :target                      -- 想选的课
   AND b.course_id IN (:my_selected_course_ids)   -- 我已选的课
   AND a.start_section <= b.end_section AND b.start_section <= a.end_section
   AND a.start_week    <= b.end_week    AND b.start_week    <= a.end_week
```

**教师排课冲突只判节次，不判周次。** 这是有意的：一位老师在同一个学期的同一天、
同一时间段只能出现在一个教室，哪怕两门课的周次区间不重合（比如一门 1-8 周、
一门 9-16 周），教务处也无法安排 —— 需要留出调课余地。
实现上就是教师冲突查询比学生冲突少一个「周次重叠」条件
（`schedule_repo` 里的两处 SQL 可以直接对照）。

这套判定在**三处**出现，且三处写法一致：

| 位置 | 作用 |
|---|---|
| `enrollment_repo.find_available_courses` | 可选课程列表：**在 SQL 里**就把已选和冲突的课排除掉 |
| `enrollment_repo.find_conflicts` | 冲突反查：反查「我选的课挡住了哪些课」，供前端黄色告警条展示 |
| `enrollment_service.select_course` | 选课校验：最终把关（前端可以被绕过，这里不能） |

> 为什么过滤放在 SQL 里而不是 Python 里？
> 因为分页。如果在 Python 里过滤，就需要先把所有课程取出来再切片，
> `total` 也会算错。放进 SQL 才能让分页、排序、过滤三者同时正确。

### 5.4 软退课

```
退课：  UPDATE enrollment SET status='WITHDRAWN' WHERE student_id=? AND course_id=?
        UPDATE course SET enrolled_count = enrolled_count - 1 WHERE id=? AND enrolled_count > 0

重选：  已有 WITHDRAWN 记录 → UPDATE 回 SELECTED，并把 score 清空
        没有记录           → INSERT 一条新记录
```

保留历史的价值：管理员能在选课记录页看到「谁选过又退了」，成绩也不会串到下一次选课。
清空旧成绩是必须的 —— 否则学生退课再选，上学期不及格的分数会直接挂在新记录上。

### 5.5 统计报表

三条报表都用了 `LEFT JOIN`，目的是**让没有数据的维度也出现在结果里**：

* 各专业选课分布：没人选课的专业也要显示 `0`，否则看起来像「专业不存在」；
* 教师工作量：没排课的教师也要显示 `0`，否则教务处会漏掉这位老师；
* 热门课程 Top-N：按选课人数倒序，附带满座率。

## 6. 开闭原则的落地

「对扩展开放、对修改关闭」在本项目里有**四个可验证的扩展点**。
判断标准很实际：**加一个新东西，需要改几个已有文件？**

### 6.1 AI 回答提供方（核心扩展点）

`ai/provider.py` 定义协议：

```python
@runtime_checkable
class AiAnswerProvider(Protocol):
    name: str                                        # 前端「来源」标签显示的名字
    order: int                                       # 越小越先被询问
    def is_available(self) -> bool: ...
    def try_answer(self, question: str, ctx: AiContext) -> AiAnswer | None: ...
```

`ai/registry.py` 是一个有序注册表。`AiService` **只做编排**，不认识任何具体提供方：

```python
class AiService:
    def __init__(self, providers: AiProviderRegistry): ...
    def ask(self, question, ctx):
        for provider in self.providers.available():   # 按 order 依次问
            answer = provider.try_answer(question, ctx)
            if answer is not None:
                return answer                          # 谁先答出来就用谁
        return FALLBACK
```

当前注册了两个：

| order | 提供方 | 说明 |
|---|---|---|
| 10 | `KnowledgeBaseProvider` | 本地知识库，关键词长度加权匹配 + 角色过滤 |
| 20 | `LlmProvider` | Anthropic 协议兼容端点；未配 `AI_API_KEY` 时 `is_available()` 返回 `False` |

**新增一个回答来源需要改的已有文件数 = 0**：

```python
class FaqProvider:            # 1. 写一个新类，实现协议
    name, order = "常见问题", 15
    def is_available(self): return True
    def try_answer(self, question, ctx): ...
```

```python
registry.register(FaqProvider())   # 2. 注册
```

开发阶段验证过：运行时注册一个新提供方，它立即参与回答且**顺序由 `order` 决定**，
全过程没有修改任何已有文件。这就是「对扩展开放、对修改关闭」的直接证据，
而不是文档里的一句声明。

### 6.2 路由注册表

```python
# routers/__init__.py
ALL_ROUTERS = [auth.router, course.router, schedule.router, ...]

# main.py
for router in ALL_ROUTERS:
    app.include_router(router, prefix="/api")
```

新增一个 REST 模块 = 写一个 `routers/xxx.py` + 往列表里追加一个元素，`main.py` 不动。

### 6.3 声明式角色权限

`require_role(*roles)` 是依赖工厂，权限写在路由签名上。
新增角色（比如「教务员」）时，已有路由一行不改，只在新路由上写 `require_role(Role.REGISTRAR)`。

### 6.4 前端视图注册表

```
static/js/router.js      路由表：路径 → 视图模块
static/js/views/index.js 视图表：模块名 → 渲染函数
static/js/layout.js      菜单数据：分组 → 菜单项 → 路径
```

新增页面 = 新增一个 view 模块 + 在三个表里各加一条记录。

三张表必须同时改，这也是这个方案唯一的代价：只改其中两张不会报错，
症状是「点菜单白屏」或「页面在但菜单里找不到」。开发阶段用一组用例
解析这三个文件的源码做过一致性校验（路由表里出现的每个路径都能在视图表里找到，
菜单里出现的每个路径都注册了路由），防止三者各改各的。

## 7. 前端设计

### 7.1 为什么手写而不是用框架

题目要求「零外部依赖可运行」。CDN 引入 Vue 需要联网，npm 构建需要 Node 环境，
两者都会让「解压即运行」失败。因此前端是手写的原生 ES Module，
由 FastAPI 的 `StaticFiles` 直接托管。

代价是组件要自己写。于是抽了一个约 400 行的组件层 `static/js/ui.js`：
`DataTable` / `Dialog` / `Confirm` / `Toast` / `Pagination` / 表单与校验 / `Progress` / `Tag` / `Tabs`。
各页面只负责「描述数据与列定义」，不重复写 DOM 结构。

### 7.2 用 hash 路由

后端用 `StaticFiles` 托管静态资源，它**没有 SPA fallback** ——
直接访问 `/admin/courses` 会 404。所以前端用 hash 路由（`#/admin/courses`），
浏览器不会把 hash 后面的内容发给服务器。

### 7.3 不使用 innerHTML

全站没有任何一处用 `innerHTML` 拼接用户数据。原因很具体：
课程名、学生姓名都是用户输入，而 **JWT 存在 `localStorage` 里** ——
一个存储型 XSS 就能把令牌读走并冒充该用户。

所以：所有文本走 `textContent`，节点走 `createElement`。
AI 回答里的 `**加粗**` 与换行也不是拼 HTML，而是逐段建 `<strong>` / `<br>` 节点：

```js
source.split('\n').forEach((line, i) => {
  if (i) fragment.appendChild(h('br'))
  line.split(/\*\*(.+?)\*\*/g).forEach((part, index) => {
    fragment.appendChild(index % 2 ? h('strong', {}, part) : document.createTextNode(part))
  })
})
```

即使回答里带了 `<script>`，也只会被当成字面量显示出来。

## 8. 安全设计

| 风险 | 措施 |
|---|---|
| 凭据泄露 | 敏感项**只从环境变量读取**，仓库内只有 `.env.example` 占位符；打包前有机械扫描门禁 |
| 口令泄露 | bcrypt 加盐哈希；数据库文件本身也被排除在提交物之外 |
| 账号枚举 | 账号不存在与口令错误返回同一条提示 |
| 越权 | 每个路由显式声明所需角色；Service 层再按 `refId` 限定数据范围（教师只能看自己的课） |
| SQL 注入 | 全部使用参数化查询，没有任何字符串拼接 SQL |
| XSS | 前端不使用 `innerHTML`；JWT 虽在 `localStorage`，但没有注入口 |
| 容量越界 | 数据库 `CHECK` 约束 + 原子 `UPDATE` 的条件双重保护 |
| 误删数据 | 有引用时拒绝删除（有选课记录的课程/学生、有课程的教师） |

`scripts/sanitize_check.py` 是**机械门禁**而不是人工检查清单，
扫描四类问题并在命中时让打包失败：`sk-` 开头的 Key 字面量、
被赋了非空值的 `api-key`、硬编码绝对路径、仓库中出现 `.env` 或 `*.db`。
`scripts/package.py` 会先调用它 —— 不通过就产不出压缩包。

## 9. SQL 方言适配

从 MySQL 8 迁移到 SQLite 时，改动集中在 SQL 层面，**业务语义完全不变**：

| MySQL | SQLite | 说明 |
|---|---|---|
| `AUTO_INCREMENT` | `INTEGER PRIMARY KEY AUTOINCREMENT` | |
| `DATETIME DEFAULT NOW()` | `TEXT DEFAULT (datetime('now','localtime'))` | SQLite 无日期类型 |
| `DECIMAL(3,1)` | `NUMERIC` + 读出后转 `float` | SQLite 无定点类型，靠列亲和性 |
| `FIELD(x, 'a','b')` | `CASE WHEN x='a' THEN 1 ...` | 自定义排序 |
| `CONCAT(a, b)` | `a \|\| b` | |
| `DATE_SUB(NOW(), INTERVAL 7 DAY)` | `datetime('now','-7 days')` | |
| `EXPLAIN` | `EXPLAIN QUERY PLAN` | 输出格式不同 |
| 表内 `KEY idx (...)` | 独立 `CREATE INDEX` | |
| `COMMENT '...'` | 行内 `--` 注释 | |
| 默认 `REPEATABLE READ` | `BEGIN IMMEDIATE` 显式写事务 | SQLite 只有库级写锁 |
