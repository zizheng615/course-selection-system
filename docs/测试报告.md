### 3.1 重点用例：并发防超卖

这是整套测试里最关键的一组。做法：

1. 造一门容量为 K 的课，剩余名额恰好 K；
2. 起 N（N > K）个线程，各自用独立的 HTTP 客户端同时发起选课；
3. 断言：**成功次数 == K**，失败的全部是 `4004 名额已满`；
4. 断言：课程 `enrolled_count == K`，且 `SELECT COUNT(*) FROM enrollment WHERE status='SELECTED'` 也等于 K。

第 4 条断言是重点 —— 它同时验证了「原子 UPDATE 没有超卖」和「冗余计数没有跑偏」。
如果只验成功次数，可能出现「计数对了但记录多了一条」的情况。

### 3.2 重点用例：开闭原则的可验证性

为了不让「满足开闭原则」停留在文档声明上，测试做了两件事：

* **后端**：在运行时构造一个新的 `AiAnswerProvider` 并注册，
  断言它立刻参与回答，且优先级由 `order` 决定；同时断言
  *没有修改* 任何已有提供方与 `AiService`。
* **前端**：读取 `router.js` / `views/index.js` / `layout.js` 三个文件的源码，
  解析出路由表、视图表、菜单表，断言三者的路径集合互相自洽
  —— 防止新增页面时只改了两处而漏掉第三处。

## 6. 缺陷记录

集成测试阶段一共发现并修复了 **6 个真实缺陷**。
它们在单元测试里全部是绿的 —— 这正好说明了端到端测试不可省略。

### 缺陷 1：异步确认回调失效，保存失败时弹窗被关闭且输入丢失

* **现象**：排课保存因教师冲突失败时，弹窗直接关掉，用户填的内容全没了，
  只有一条一闪而过的提示。
* **根因**：`ui.js` 的 `openDialog` 里判断 `if (onConfirm() === false) return`，
  但 `onConfirm` 是 `async` 函数，返回的是 **Promise 对象**，
  与 `false` 比较永远不成立 —— 「返回 false 表示校验没过」这个约定从未生效过。
* **修复**：`await` 之后再比较，并在请求期间禁用按钮防止连点重复提交。

### 缺陷 2：排课表单缺少跨字段校验，错误只能由后端发现

* **现象**：把「开始节次」填得比「结束节次」大，前端毫无反应，
  提交后靠后端返回错误。
* **根因**：表单校验框架只支持单字段规则（必填、范围），
  而「起止先后」是跨字段的。
* **修复**：给结束字段挂一个 `notBefore(label, startNode)` 校验器，
  读取同一表单里另一个节点的当前值。错误显示在「结束节次」下方，定位准确。

### 缺陷 3：AI 抽屉的「发送」按钮点不动

* **现象**：抽屉打开后，点「发送」没反应。Playwright 报
  `<button class="fab"> intercepts pointer events`。
* **根因**：悬浮球 `.fab` 固定在右下角，抽屉打开后它正好压在抽屉底部的
  「发送」按钮上，而且 `z-index` 比抽屉还高，把所有点击都吃掉了。
* **修复**：抽屉打开时（`body.ai-open`）把悬浮球左移到抽屉外侧；
  同时它也顺理成章地变成了「收起抽屉」的按钮。

### 缺陷 4：AI 回答里的 Markdown 加粗显示为字面星号

* **现象**：回答里出现「左侧 \*\*课程管理\*\*」这样的原始星号。
* **根因**：知识库条目确实带 `**`（与参考项目一致），但前端只做了纯文本渲染。
* **修复**：新增 `richText()`，把 `**..**` 与换行转成真实的 `<strong>` / `<br>` 节点。
  **没有使用 `innerHTML`** —— 保持全站无 XSS 注入面的策略。

### 缺陷 5：冲突提示条文案混乱

* **现象**：告警条显示「《数据结构》—— 线性代数」，看不出谁和谁冲突。
* **根因**：早期实现只把两个课程名拼在一起。
* **修复**：改为与参考项目一致的措辞：先给结论
  「以下课程因时间冲突不可选：」，再逐门课用标签标明
  「数据结构（与「线性代数」时间冲突）」。

### 缺陷 6（最严重）：切换账号后 AI 助手残留上一位用户的状态

* **现象**：退出登录再登录另一个角色后，页面上出现 **两个悬浮球**；
  并且新用户打开抽屉时，看到的是**上一位用户的欢迎语和推荐问题**。
* **根因**：`mountAssistant()` 把抽屉和悬浮球挂在 `<body>` 上，
  而主布局重挂载时只清空了 `#app` —— 于是每换一次账号就多叠一份，
  上一份还带着上一位用户的姓名与角色化推荐问题。**这是角色隔离被破坏**，
  不只是界面重复。
* **修复**：`mountAssistant()` 开头先把上一份抽屉/悬浮球从 DOM 摘掉，
  并重置 `ai-open` 状态与「推荐问题已加载」标志。
* **验证**：登录 → 退出 → 换角色登录，全程断言
  `document.querySelectorAll('button.fab').length === 1`；
  换账号后欢迎语正确变为新用户的姓名与角色化问题。
* **备注**：这个缺陷只在「切换账号」这条路径上出现，
  单元测试和单角色集成测试都发现不了。

### 6.1 测试过程中的两个环境陷阱（非产品缺陷）

记录下来供后续复现参考：

* **`localStorage.clear()` 必须配合页面刷新**。应用的登录态同时存在于
  `localStorage` 与内存中的 `store` 对象；只清 `localStorage` 而不刷新，
  内存里仍是旧用户的身份，会出现「明明清了还是登录状态」的假象。
* **自动化工具的输入偶发失效**。长时间驱动同一个页面后，
  Playwright 的鼠标事件可能不再送达页面（表现为点击无任何事件产生）。
  这不是应用问题 —— 重建页面后一切正常。判断方法：在 `document` 上挂捕获监听，
  若连监听器都收不到事件，即可确定是驱动侧而非应用侧。
